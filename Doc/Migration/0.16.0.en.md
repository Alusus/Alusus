# Alusus 0.16.0: Migration Notes for Dependent Projects

This document is for developers and AI agents updating Alusus-based libraries and projects to the 0.16.0
compiler and standard library. It lists what changed, what can break existing code, and the pitfalls we hit
while implementing these changes. Everything here was verified against the Alusus sources in this repo; the
user-facing changelog is in `changelog.en.md` / `changelog.ar.md`, and API reference pages are under
`Doc/Srt_Reference/`.

Naming follows the project convention: English identifiers with Arabic aliases where they exist.

## 1. API changes

### Module and type structure

- The `Core::Data` namespace has been removed. AST classes now live in `Core.Ast` (`Core::Ast`), and grammar
  classes in `Core.Grammar`. Update any `Core.Data.*` references to the new names.
- All AST classes are now derived from `Core.Ast.Node`. Child AST nodes are held as `Node`, and the
  containers that hold them are `Containing[Node]` (and `DynamicContaining[Node]`, etc.), rather than
  `Containing[TiObject]`. Code that stored or iterated children as `TiObject` must switch to `Node`.
- The `Containing` interface on the Alusus side is now template based. It's declared as
  `Containing[ContentType: type]`, so it's instantiated for a concrete element type, e.g.
  `Core.Basic.Containing[Core.Ast.Node]`. The same applies to `DynamicContaining`, `MapContaining`, and
  `DynamicMapContaining`.

### Node metadata (`Core.Ast.Node`)

Metadata is a per-node property. The methods operate on the node they're called on; they do **not** walk up to
the owning Definition.

| Alusus (English) | Arabic alias | Signature |
|---|---|---|
| `getMetadata` | `هات_بيانات_وصفية` | `(name: ptr[array[Char]]): ref[SrdRef[Node]]` (null if unset) |
| `setMetadata` | `حدد_بيانات_وصفية` | `(name: ptr[array[Char]], value: ref[SrdRef[Node]])` |
| `removeMetadata` | `أزل_بيانات_وصفية` | `(name: ptr[array[Char]])` |

Bound through `Sources/Core/interop.cpp` (`CoreAstNode_*`) and `Sources/Srt/Core/Ast.alusus`.

Note: an earlier version of these methods lived on `Spp.astMgr`. They were removed. Do not call
`Spp.astMgr.getMetadata` and friends.

### Containing search (`Core.Basic.Containing`)

- `findElementIndex(val: ref[ContentType]): Int`: index of `val` by identity, or `-1`.
  Arabic: `جد_تسلسل_عنصر`. Implemented as a default virtual in `Sources/Core/Basic/Containing.h`, so no
  existing implementor needed changes.

### Merge-aware insertion (`Spp.astMgr`)

- `addPossiblyMergeableElement(node: ref[AstNode], target: ref[DynamicContaining[AstNode]], index: ref[Int]): Bool`
  Arabic: `أضف_عنصرا_قابلا_للدمج`.
  - `index` is in/out: pass `-1` to append; otherwise it's the insertion position and is advanced past the
    inserted element(s), so you can chain calls.
  - Unwraps `MergeList`s. Does **not** unwrap `Block`/`Scope` (see gotchas).
  - Merges `@merge` definitions into existing matches.

### Seeker criteria (`Spp.astMgr.findElements`)

- New criterion `metadata == "name"`: matches elements whose owning Definition has metadata `name` set,
  regardless of value. Arabic: `بيانات_وصفية == "..."`.
- `findElements` is for **named** elements only (variables, functions, types, modules), resolved the way
  identifiers are. It is not a general AST search. For a general traversal, use `Containing` /
  `DynamicContaining` directly. The docs say this explicitly now.
- `modifier` and `metadata` criteria look at the owning Definition (`target->getOwner()`), not arbitrary
  nodes. This is intentional and is not planned to change.

## 2. Behavior changes that can break existing code

### Unhandled modifiers are now a compile error

Any modifier that the grammar doesn't handle itself must resolve to a handler function. The handler is looked
up by the modifier's name (or dotted qualifier) and must take two `ref[Core.Ast.Node]` arguments: the element
the modifier is attached to, and the modifier's params (null if none). If no handler is found, the compiler
emits:

```
CP1005: Unexpected modifier encountered.
```

Previously these were silently ignored. This is intentional, so typos in modifier names are caught. Any
library that uses custom modifiers without a handler must be fixed: write the handler, or remove the modifier.

Concrete cases seen in this repo's sources:

- `@shared` on a **function** is invalid. `shared` only applies to variables. It shows up in
  `Srl/Memory.alusus`, `Core.alusus`, and `Spp.alusus` in some builds.

### Dotted (qualified) modifier names

`@Module.modifier[args] <definition>` is accepted, and the dotted chain is resolved as a full qualifier, so
the handler can live anywhere in the code base. This relies on the `root.Modifier.Expression.FunctionalExp`
grammar override in `Sources/Core/Grammar/StandardFactory.cpp`. As of HEAD, its `dup` value is `0`, which the
user set manually. The user has reported that the dotted-qualifier error is resolved.

## 3. Pitfalls and gotchas

These are the non-obvious things we hit. Each one cost real debugging time.

1. **Don't create nodes with a factory inside a modifier handler and keep them.** For example,
   `Core.Ast.IntegerLiteral.create(...)` called from a handler and then stored in the AST crashes at program
   exit. Use `Spp.astMgr.cloneAst(...)` to produce nodes that a handler stores.

2. **For a `def` statement, the modifier handler's first argument is the Definition.** `X~ast` for a variable
   resolves to its value/type node, one level below the Definition. So query metadata on `X~ast.owner`, not on
   `X~ast`. Verified with `getMyTypeInfo().typeName`.

3. **`ast { ... }` / `شبم { ... }` always produces a Block/Scope**, even for one statement. `cloneAst`,
   `buildAst`, and `addPossiblyMergeableElement` do not unwrap it. Unwrap manually before inserting:
   ```
   def container: Core.Basic.ContainerOf[newNode.obj, Core.Ast.Node];
   def actual: ref[Core.Ast.Node](container.getElement(0));
   ```
   A bare expression such as `ast { 1 }` is not wrapped.

4. **Replacing a definition**: get the index with `ContainerOf[node.owner].findElementIndex(node)`, then
   `DynContainerOf[node.owner].removeElement(index)`, then `addPossiblyMergeableElement(actual, dynOwner, index)`.
   Renaming a definition in place works through `Core.Basic.BindingOf[node].setMember("name", newName)`.

5. **`Spp.astMgr.getDefinitionName(x~ast)` fails to compile even for a plain top-level variable.** This is a
   pre-existing issue and not caused by 0.16.0. Use a local helper that reads the name through Binding instead:
   ```
   function getDefName(element: ref[Core.Ast.Node]): String {
       def d: ref[Core.Ast.Definition](castRef[element.owner, Core.Ast.Definition]);
       def binding: ref[Core.Basic.Binding](Core.Basic.getInterface[d, Core.Basic.Binding]);
       return castRef[binding.getMember("name"), Core.Basic.TiStr].value;
   }
   ```

6. **`StringLiteral.value` is a `TiStr`, and `TiStr.value` is the `String`.** To get characters from a
   `StringLiteral`, use `str.value.value.buf`. In Arabic code: `.القيمة.القيمة.صوان`.

7. **Arabic files need explicit imports.** `سـندنا` needs `اشمل "مـتم/سندات"؛` and `نـص` needs
   `اشمل "مـتم/نـص"؛`, even when `نـبم` pulls in the English equivalents transitively.

8. **Argument order and `ref[SrdRef[...]]`.** `setMetadata`/`getMetadata` take and return
   `ref[SrdRef[Node]]`, which maps to `SharedPtr<Node> const&` in C++. Passing a call's temporary result
   directly works. Assigning to a local first also works. Use whichever reads better.


## 4. Checklist for updating a dependent project

1. Build against the 0.16.0 compiler.
2. Search for any uses of `Core.Data.Ast` module and replace it with `Core.Ast`.
3. Search for uses of `Core.Basic.TiObject` with AST nodes and replace that with `Core.Ast.Node`. This includes
   replacing the `Containing[TiObject]` with `Containing[Core.Ast.Node]`.
4. Search the project for custom modifiers (`@`) that have no handler function, and for `@shared` on
   functions. Fix each one (section 2). For each custom modifier that the project relies on:
   - Write a modifier handler function with the signature `(node: ref[Core.Ast.Node], params: ref[Core.Ast.Node])`
     that stores the modifier's params as metadata on `node`, using `Spp.astMgr.cloneAst(params, params)` to
     create the stored value (gotcha 1). The handler's `node` is the Definition the modifier is attached to.
   - Update every place that looked for the modifier through `Spp.astMgr` (`findModifier`,
     `findModifierForElement`, `getModifierStringParams`, `findElements` with `modifier == "..."`, etc.) to
     look for the metadata instead: read it with `element.owner.getMetadata("name")` on the value/type node
     of the definition, or find elements with `findElements` using `metadata == "name"`. Read the stored
     params from the returned node the same way as any other `Containing[Node]` / `StringLiteral` value.
5. For any `.create()` call inside a modifier handler whose result is kept, switch to `cloneAst` (gotcha 1).
6. Run the project's tests. If a test fails at program exit, check gotcha 1 first.
