# Alusus 1.0.0: Migration Notes for Dependent Projects

This document is for developers and AI agents updating Alusus-based libraries and projects from 0.16.0 to the
1.0.0 compiler and standard library. It only covers the changes that can stop existing code from compiling, or
make it behave differently, and how to update the code. New features that don't affect existing code are listed
in `changelog.en.md`, and API reference pages are under `Doc/Srt_Reference/`.

## 1. Syntax changes

### `def name: type = value` is no longer accepted

The `def` command no longer accepts the `=` operator. Code like this:

```
def count: Int = 0;
def name: String = "Alusus";
```

now fails with:

```
CD1003: Invalid 'def' command.
```

Use the new `var` command instead:

```
var count: Int = 0;        // Constructs with no args, then assigns 0.
var name: String = "Alusus";
var total = a + b;         // The type is deduced from the value.
```

Mapping old code to new code:

| 0.16.0 | 1.0.0 |
|---|---|
| `def x: T = v;` | `var x: T = v;` (or `var x = v;` to deduce the type) |
| `def x: T(args);` | Unchanged. `var x: T(args);` works too. |
| `def x: T;` | Unchanged. |

Notes:

- `var x: T = v` keeps the old semantics of `def x: T = v`: the variable is constructed without args and then `v`
  is assigned to it. To pass the value to the constructor instead, use `var x := v` (type deduced) or
  `var x: T(v)`. `var x: T := v` is an error (SPPH1027).
- This also applies to member variables (`var a: Int = 3;` inside a class) and to `@shared` variables.
- Global variables defined with `var` get their values assigned in the global constructors, so the assignment is
  also included in offline (executable) builds.

### New keywords: `var`, `within`

`var` and `within` are now keywords. Any identifier with one of these names that is used at the start of a
statement must be renamed.

## 2. Import changes

### Import `compiler` instead of the individual Core/Spp files

The library files of the compiler interop (`Core`, `Core/Basic`, `Core/Ast`, `Spp`, and `Spp/Ast`) no longer
import their own dependencies. Importing one of them alone now fails with errors such as `SPPA1007: Unknown symbol.` reported
inside the library file itself.

Replace them with a single import:

```
import "compiler";
```

For example:

```
// 0.16.0
import "Core/Ast";
import "Spp";

// 1.0.0
import "compiler";
```

`Srl` imports (`Srl/String`, `Srl/Console`, etc.) are unaffected.

## 3. Standard library changes

### Removed or renamed definitions

| 0.16.0 | 1.0.0 |
|---|---|
| `Spp.AstNode` | `Core.Ast.Node` |
| `Core.Ast.MergeList` | `Core.Ast.Within` (see section 5) |
| `Definition`'s `target` property (e.g. `BindingOf[def].getMember("target")`) | `subject` |

### `true` and `false` are now `Bool`

`true` and `false` are now defined as `1i1` and `0i1`, i.e. of type `Bool` (`Word[1]`)
rather than plain integer literals. Assigning them to integer variables still works, but they can resolve
differently in overload selection, so `f(true)` may now pick an `f(Bool)` overload over an `f(Int)` one.

### `Process.platform`, `Process.language`, and `Process.coreBinPath` are constants

They can no longer be assigned to. Code that overwrote them (e.g. in tests) must use its own variable instead.

### `Srl.System` signatures

`System.getEnv` now returns a `CharsLptr` (see the next section). Storing the result in a `CharsPtr` still
works since `lptr` casts implicitly to `ptr`.

## 4. String literals and `lptr`

String literals are now of type `lptr[array[Word[8]]]` (alias `CharsLptr`) instead of `ptr[array[Word[8]]]`. An `lptr` casts implicitly to `ptr`, so passing a literal to a `CharsPtr`
parameter, or assigning it to a `CharsPtr` variable, still works. What breaks:

- Casting a `ptr` to an `lptr` must be done explicitly. Code that assigns a `CharsPtr` to a variable whose type
  was deduced from a literal (e.g. `var s = "x"; s = someCharsPtr;`) now fails with
  `SPPG1015: Incompatible types for the given operator.` Declare the variable as `CharsPtr` instead
  (`var s: CharsPtr = "x";`), or cast explicitly.
- Code that inspects the type of a literal (`"abc"~type`, template args deduced from literals, macros that
  generate types from literal values) now gets `lptr[...]`.
- String literals now cast implicitly to `String`. Overload sets that accept both a pointer and a `String` still
  prefer the pointer overload, but a function that only had a `String` overload and an overload of some other
  type that a literal could also be cast to may now become ambiguous.

## 5. Compiler behavior changes

### Members are accessible from methods without `this.`

`this` is now implicitly injected into every method body. Names inside a method are looked up in this order:
the method's local variables and arguments, then the members of the object, then everything outside the type.
This means that **a method that referred to a global definition whose name matches a member of the class now
silently refers to the member instead**. For example:

```
def count: Int;
class C {
    def count: Int;
    handler this.inc() { count = 7 }  // 0.16.0: global `count`. 1.0.0: `this.count`.
}
```

Review methods that use global names which are also member names, and qualify them (e.g. `Main.count`, or
`Root.count` for root-level definitions). If a member must not be reachable implicitly, mark it with the new
`@not_injected` modifier.

Related name lookup changes:

- Injections within a function's body no longer hide the function's arguments or local definitions.
- A name found through an injection, a `use` statement, or an outer scope no longer hides definitions with the
  same name further out when it doesn't match the given args. Code that relied on an inner, non-matching
  definition to cause an error, or on a specific shadowing order, may now resolve to a different definition.

### Named `as_ptr` and `set_ptr` handlers define backing methods

`handler this.f() as_ptr { ... }` now also defines a method named `_f` and sets the pointer `f` to it. The same
applies to `set_ptr` handlers. Consequences:

- A class that already has a member called `_f` next to an `as_ptr`/`set_ptr` handler named `f` now gets an
  `SPPA1005: Multiple matches were found for the given callee` error. Rename the existing member.
- Overriding pointers with the same name and type from two different members of the same class (e.g. multiple
  inheritance where both parents have a `f` pointer) is now an error, since both overrides would define `_f`.
  Set those pointers manually to methods with distinct names.

### `@no_bind` applies to explicit member access

The `@no_bind` modifier now also applies when the member is accessed explicitly, not only through injection.
With `@no_bind var vtable: ref[VTable]`, `t.vtable.getVal()` now calls `getVal` with `t` as `this` instead of
`t.vtable`. Code that accessed a `@no_bind` member explicitly and expected the member itself to be `this` must be
updated.

### `~size` returns `ArchWord`

`T~size` now always returns an `ArchWord` instead of the smallest signed integer type that fits the size.
Assigning it to an `Int` still works, but watch for:

- Passing `~size` to variadic functions such as `Console.print`: use `%ld` (or cast to `Int`) instead of `%d`.
- Mixing `~size` with signed values in comparisons or subtraction, which now happens in unsigned arithmetic.

### Calls on types pick the best match

A call like `MyType(...)` now considers constructors, `()` operators on the type (`this_type`), and `()`
operators on an object (`this`) together, and picks the best match. Previously the first `()` operator found won
even if a constructor matched better. Types that define both may now resolve such calls to a different function.
If a `()` operator and a constructor match equally well, the `()` operator still wins.

### Build errors and exit codes

- The `alusus` executable now exits with a failure code whenever an error was reported while building the
  program, even if the parts that built successfully were executed. Scripts and CI that ran programs with
  known, ignored build errors will now see a failing exit code. Fix the errors.
- Execution no longer stops at the first build error. Statements, including `preprocess` statements, after a
  build error still run if they and their dependencies built successfully. Output of programs with build errors
  may therefore differ from 0.16.0.

## 6. AST and compiler interop

### `MergeList` is replaced by `Within`

`Core.Ast.MergeList` was removed. Code that created a `MergeList` to insert several elements at once, e.g. from
a `preprocess` block or through `Spp.astMgr.addPossiblyMergeableElement`, should create a `Core.Ast.Within`
instead:

```
// 0.16.0
def assignments: SrdRef[MergeList] = newSrdObj[MergeList];

// 1.0.0
var assignments: SrdRef[Within] = newSrdObj[Within];
```

`addPossiblyMergeableElement` and `insertAst` expand a `Within` the same way they expanded a `MergeList`. A
`Within` that has a qualifier adds its elements to the scope the qualifier points to.

### AST class members are properties

AST classes in `Core.Ast` and `Spp.Ast` now have generated property accessors for their members (e.g.
`def.name.value`, `link.first = node`). Existing code that goes through `Binding` / `MapContaining` still works.
The one change to watch is in text-based nodes (`Identifier`, `StringLiteral`, etc.), whose `value` member is now
an accessor instead of a plain member. Reading `node.value.value` is unchanged, but code that depended on the
class layout (e.g. `~size` of these classes, or padding computed from `TiStr~size`) must be updated.

### Definition `target` renamed to `subject`

In both C++ (`Definition::getTarget`/`setTarget` → `getSubject`/`setSubject`) and Alusus code (the `"target"`
member name in `Binding` calls, or the new `subject` property), the definition's target is now called `subject`.

## 7. C++ extensions

This only affects projects that extend the compiler in C++.

- `Core/Basic/ti_functions.h` was renamed to `Core/Basic/ti_callees.h`. The slow `call()` helpers and the
  `TiCallee*` override variants were removed.
- Bound methods are now plain function pointers rather than `std::function`, and they no longer receive a
  `TiFunctionBase *base` first argument. Update override functions from:
  ```
  static void _f(TiFunctionBase *base, TiObject *self, ...);
  ```
  to:
  ```
  static void _f(TiObject *self, ...);
  ```
- `useCallee(base)(...)` was replaced by `callSuper(...)` on the binding cache that set the override. Declare a
  binding cache for the method in the extension, bind it with `init(owner, &Extension::_f)` in the extension's
  `initBindingCaches`, and call `this->f.callSuper(...)` to call the overridden implementation.
- Overrides set through a binding cache are removed automatically when the cache is destroyed, so the
  `Overrides` structs that were returned by `extend` and passed to `unextend` are no longer needed. Removing the
  extension's dynamic interface removes its overrides.
- `Core::Ast::MergeList` was replaced by `Core::Ast::Within`, and `Seeker` has a new `add` operation that can
  be overridden to support more kinds of `within` targets.

See `Sources/Spp/RootScopeHandlerExtension.{h,cpp}` for a complete example of the new pattern.

## 8. Checklist for updating a dependent project

1. Build against the 1.0.0 compiler.
2. Replace `def name: type = value` with `var name: type = value`. Search for `CD1003` errors to find the
   remaining ones.
3. Rename any identifiers called `var` or `within`.
4. Replace imports of `Core`, `Core/Basic`, `Core/Ast`, `Spp`, and `Spp/Ast` with `import "compiler"`.
5. Replace `Spp.AstNode` with `Core.Ast.Node`, `MergeList` with `Within`, and the definition's `target` with
   `subject`.
6. Remove any assignments to `Process.platform`, `Process.language`, or `Process.coreBinPath`.
7. Fix explicit `ptr` → `lptr` conversions reported as `SPPG1015` (section 4).
8. Review methods that refer to global names also used by class members (section 5), and members named `_f`
   next to `as_ptr`/`set_ptr` handlers named `f`.
9. Check format strings that print `~size` values.
10. For C++ extensions, follow section 7.
11. Run the project's tests and make sure the exit code is zero, since build errors now fail the run.
